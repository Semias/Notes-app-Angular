# Notes Backend

Go REST API backing the Angular notes app. Postgres for storage, `goose` for
migrations, `sqlc` for type-safe queries, and Go's standard library for routing.

Serves `http://localhost:5000`, which is where the Angular dev build points
(`Frontend/src/environments/environment.ts`). To deploy frontend and backend
together, see `docker-compose.yml` in the repo root.

---

## Prerequisites

| Tool | Check | Install |
|---|---|---|
| Go 1.22+ | `go version` | `winget install GoLang.Go` |
| Docker Desktop | `docker info` | Must be **running**, not just installed |
| goose | `goose -version` | `go install github.com/pressly/goose/v3/cmd/goose@latest` |
| sqlc | `sqlc version` | `go install github.com/sqlc-dev/sqlc/cmd/sqlc@latest` |

`goose` and `sqlc` install into `$(go env GOPATH)\bin`. If the commands are not
found, that directory is not on your `PATH`.

## Project structure

```
Backend/
├── main.go                  Bootstrap only: config, database, wiring, serve
├── middleware.go            CORS - applies to every route, so it lives app-level
├── sqlc.yaml                Code generation settings
├── .env                     Real credentials (git-ignored)
├── .env.example             Template - commit this, never .env
│
├── sql/
│   ├── queries.sql          Hand-written SQL; the source for sqlc
│   └── migrations/          Schema history, applied by goose in order
│
└── internal/
    ├── database/            GENERATED by sqlc - never edit by hand
    └── notes/               The notes feature module
        ├── module.go        Assembles the layers; the only entry point main.go uses
        ├── controller.go    HTTP: routes, status codes, JSON
        ├── service.go       Business logic and domain errors
        ├── entity.go        Note domain entity + mapping from the database row
        └── dto.go           Incoming request shape, normalization, validation
```

**The layering runs one direction only:**

```
controller  ->  service  ->  database (sqlc)
```

The controller knows HTTP but never touches `pgx`. The service knows `pgx` but
never imports `net/http` — it returns domain errors like `ErrNotFound`, and the
controller decides those become a `404`. That keeps the service callable from a
test or a CLI without dragging a web server along.

Adding a second feature (say, tags) means creating a sibling package with the
same five files — not growing this one.

## First-time setup

```powershell
# 1. Credentials
Copy-Item .env.example .env
#    then edit .env and set a real POSTGRES_PASSWORD,
#    making sure DATABASE_URL repeats the same user/password/db

# 2. Start Postgres
docker compose up -d

# 3. Create the schema
$env:GOOSE_DRIVER  = "postgres"
$env:GOOSE_DBSTRING = (Get-Content .env | Select-String '^DATABASE_URL=').ToString().Split('=',2)[1]
goose -dir sql/migrations up

# 4. Generate the query layer
sqlc generate

# 5. Run
$env:DATABASE_URL = $env:GOOSE_DBSTRING
go run .
```

You should see:

```
Starting Go backend server on http://localhost:5000...
```

> `.env` is git-ignored on purpose. When you change any of `POSTGRES_USER`,
> `POSTGRES_PASSWORD` or `POSTGRES_DB`, update `DATABASE_URL` in the same file to
> match — nothing checks that they agree, and a mismatch shows up as a confusing
> auth error at startup.

## Running day to day

```powershell
docker compose up -d          # start Postgres (safe to re-run)
$env:DATABASE_URL = "postgres://admin:YOUR_PASSWORD@localhost:5432/notes_db?sslmode=disable"
go run .                      # start the API
```

Stop the API with `Ctrl+C`. Stop the database with `docker compose down` — the
data survives, because it lives in a named volume rather than the container.

To build a standalone binary instead of `go run`:

```powershell
go build -o notes-backend.exe .
.\notes-backend.exe
```

## Migrations

A migration is one SQL file describing a schema change and how to undo it. Goose
applies them in filename order and records which have run in a `goose_db_version`
table, so each one runs exactly once.

All commands below assume these are set:

```powershell
$env:GOOSE_DRIVER   = "postgres"
$env:GOOSE_DBSTRING = "postgres://admin:YOUR_PASSWORD@localhost:5432/notes_db?sslmode=disable"
```

### See what has been applied

```powershell
goose -dir sql/migrations status
```

### Create a new migration

```powershell
goose -dir sql/migrations create add_note_colour sql
```

That writes a timestamped stub. Fill in both halves:

```sql
-- +goose Up
ALTER TABLE notes ADD COLUMN colour TEXT NOT NULL DEFAULT 'default';

-- +goose Down
ALTER TABLE notes DROP COLUMN colour;
```

Always write the `Down` section. It costs one line now and is the only thing that
makes a bad migration reversible later.

### Apply / roll back

```powershell
goose -dir sql/migrations up         # apply everything outstanding
goose -dir sql/migrations down       # undo the most recent one
goose -dir sql/migrations reset      # undo everything (destroys all data)
```

### After any schema change, regenerate

```powershell
sqlc generate
```

`sqlc` reads `sql/migrations/` as the schema and `sql/queries.sql` as the query
set, then rewrites `internal/database/`. **Skipping this step is the usual cause
of a confusing compile error** — your Go code still refers to the old columns.

The full loop for a schema change is:

```
edit migration  ->  goose up  ->  edit queries.sql  ->  sqlc generate  ->  go build
```

## API

| Method | Path | Body | Success | Errors |
|---|---|---|---|---|
| `GET` | `/notes` | — | `200` array, pinned first | |
| `GET` | `/notes/{id}` | — | `200` note | `400` bad id, `404` missing |
| `POST` | `/notes` | note | `201` created note | `400` bad JSON or blank title |
| `PUT` | `/notes/{id}` | note | `200` updated note | `400`, `404` |
| `DELETE` | `/notes/{id}` | — | `204` no content | `400` bad id |

Request body for `POST` and `PUT` — `PUT` is a full replacement, not a patch:

```json
{ "title": "Shopping", "content": "Milk, eggs", "tags": ["home"], "isPinned": false }
```

`tags` may be omitted and defaults to `[]`. `title` is required and must not be
blank. Response adds `id`, `createdAt` and `updatedAt`:

```json
{
  "id": 1,
  "title": "Shopping",
  "content": "Milk, eggs",
  "tags": ["home"],
  "isPinned": false,
  "createdAt": "2026-08-30T17:31:04.627957+02:00",
  "updatedAt": "2026-08-30T17:31:04.627957+02:00"
}
```

CORS allows `http://localhost:4200` only. Change `frontendOrigin` in
`middleware.go` if the Angular dev server moves.

## Troubleshooting

**`DATABASE_URL is not set`** — the variable is per-terminal and does not persist
between sessions. Set it again in the new shell.

**`Unable to reach database`** — Postgres is not running or the credentials are
wrong. Check `docker compose ps`, then confirm `DATABASE_URL` matches the
`POSTGRES_*` values in `.env`.

**`password authentication failed`** — usually means `.env` was edited *after* the
container was first created. Postgres only runs its initialization on an empty
data directory, so changing `POSTGRES_USER` later has no effect on the existing
volume. Either create the role by hand, or wipe and recreate:

```powershell
docker compose down -v && docker compose up -d   # DESTROYS all note data
goose -dir sql/migrations up                     # recreate the schema
```

**API returns `{"ID":1,"Title":...}` in PascalCase** — `sqlc.yaml` lost its
`emit_json_tags` settings. Restore them and re-run `sqlc generate`. Angular reads
every field as `undefined` when this happens, so notes render blank with no error.

**Port 5000 already in use** — something else holds the port:

```powershell
Get-NetTCPConnection -LocalPort 5000 | Select-Object OwningProcess
```
